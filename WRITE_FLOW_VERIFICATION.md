# Write Flow Verification Plan

Plan date: 2026-07-20

## Purpose

Verify that the BaaS migration preserves the old production UI write behavior without changing page interactions.

This plan is intentionally separated from the static audit because these checks mutate BaaS records.

- Confirm the test project name does not already exist, or explicitly reuse and clean an old test project.

## Test Matrix

### 1. Create Project

Actions:

- Open new project page.
- Fill basic project info with the test prefix.
- Select a stage and several features.
- Include at least one feature with notes.
- Save.

Expected result:

- A project record is created.
- Selected project feature records are created.
- Global access-step records are initialized.
- Timeline records are created.
- Success state and project detail navigation work.

Rollback:

- Delete the test project and related records from BaaS if the UI has no delete-project entry.

### 2. Edit Project

Actions:

- Open the test project's edit page.
- Change basic fields.
- Add one feature.
- Remove one removable feature.
- Edit notes or player-info extra config if available.
- Save.

Expected result:

- Project fields persist after reload.
- Added feature appears in project detail.
- Removed feature no longer appears.
- Notes/config persist and unrelated fields remain unchanged.

Rollback:

- Restore the test project to a disposable state or delete it after all checks.

### 3. Project Detail Status Updates

Actions:

- Change one feature status from the detail page.
- Toggle one global access step.
- Drag one card across kanban columns if available.

Expected result:

- Status persists after reload.
- Progress statistics update.
- Timeline records are appended.
- No duplicate or broken timeline entries appear.

Rollback:

- Revert the test feature status if needed, then delete test records after all checks.

### 4. Project List Status And Sorting

Actions:

- Change the test project's status from the list if the UI exposes it.
- Drag-sort the test project.
- Reload.

Expected result:

- Status and sort order persist.
- Paused projects remain grouped at the bottom according to old production behavior.
- Home statistics update correctly.

Rollback:

- Restore status or delete test project.

### 5. Sync Progress Image

Actions:

- Open the sync-progress/export action on the test project.
- Generate the progress image.

Expected result:

- Image renders with the old production layout.
- Project name, stage, feature progress, and global steps display correctly.
- No missing text, `NaN`, or broken visual blocks.

Rollback:

- No database rollback expected unless the action writes timeline records.

### 6. Admin Feature CRUD

Actions:

- Login/open admin gate only with permission.
- Create a feature with the test prefix.
- Edit the test feature.
- Soft-delete the test feature.

Expected result:

- Feature appears after create.
- Changes persist after edit.
- Soft-deleted feature disappears from active feature lists.
- Existing production features are not changed.

Rollback:

- Keep the test feature inactive or remove it directly from BaaS if needed.

### 7. Admin Document CRUD

Actions:

- Create a document with the test prefix.
- Edit it.
- Delete it.

Expected result:

- Document appears in admin and document center after create.
- Edited fields persist.
- Deleted document disappears.
- Existing production documents are not changed.

Rollback:

- Delete any leftover test document records.

## Completion Criteria

The BaaS migration write flow can be considered verified only when:

- All checked flows pass against controlled test data.
- No browser console errors occur during the write flows.
- Reload checks prove data persisted in BaaS.
- All test data is either cleaned up or explicitly retained as test data.
- The release checklist is updated with the verification result.

## Data Impact And Rollback Plan

Expected mutable collections during verification:

- `projects`: test project created or edited.
- `project_features`: feature links for the test project, including status and notes/config changes.
- `project_global_steps`: access-step completion records for the test project.
- `project_timeline`: timeline rows generated by create/status/step/drag actions.
- `features`: only touched by custom feature creation or admin feature CRUD test items.
- `documents`: only touched by admin document CRUD test items.

Expected read-only collections during verification:

- `stages`
- `access_steps`
- `system_config`

Recommended cleanup order if test data must be removed manually from BaaS:

1. Find the test project by `game_name` prefix `[BAAS迁移验证]` and record its BaaS document `id`.
2. Delete `project_timeline` rows where `project_id` equals the test project id.
3. Delete `project_global_steps` rows where `project_id` equals the test project id.
4. Delete `project_features` rows where `project_id` equals the test project id.
5. Delete the `projects` test project row.
6. For admin feature tests, remove or keep inactive any `features` rows whose `name` starts with `[BAAS迁移验证]`.
7. For admin document tests, delete any `documents` rows whose `title` starts with `[BAAS迁移验证]`.

Important cleanup note:

- Do not delete shared `stages`, `access_steps`, `system_config`, or existing non-test project data.
- Do not delete existing real `features` or `documents` unless the title/name starts with the test prefix.
